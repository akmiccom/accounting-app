# 電子帳簿保存法を意識した証憑管理

> この文書はシステム設計上の運用方針であり、税務判断そのものではない。制度改正があり得るため、本番運用開始時および年度切替時に国税庁の最新資料を確認する。

## 基本方針

会計処理の利便性だけでなく、利用者自身が必要な証憑を検索・閲覧でき、原本・取込履歴・仕訳との対応を追跡できることを重視する。

## 電子取引データ

メール添付PDF、Webからダウンロードした領収書・請求書など、最初から電子で受領したものは電子データとして保存する。

システムでは次を保持する。

- 原本ファイル
- 取引日
- 金額
- 取引先
- receipt_code
- 原本ファイル名
- MIME type
- Storage bucket/path
- SHA-256
- 登録日時
- source_system / source_record_id等の追跡情報

日付・金額・取引先で検索できるようにする。

## 不明項目

歴史データ移行やAI読取で、取引日・金額・取引先を確定できない場合は推測して補完しない。
NULLまたは要確認として保持し、後から根拠を確認できた場合のみ訂正する。

## 紙の領収書をスキャンする場合

紙を廃棄してスキャンデータを正式保存にする場合は、スキャナ保存の要件を満たす必要がある。

本システムが正式運用へ入る前に、撮影/読取条件と運用手順を確定する。

## 真実性

技術面では次を採用する。

- 証憑ファイルを原則上書きしない
- SHA-256を登録時に計算して保存する
- 証憑差替えは新規receiptとして保存する
- supersedes_receipt_idで訂正前後を追跡する
- audit_logsで操作履歴を残す
- import元ファイルもハッシュと取込日時を保存する
- 元CSV、MF raw、証憑原本の再現可能性を維持する

必要に応じて訂正・削除防止に関する事務処理規程を整備する。

## 可視性

- 証憑は画面から速やかに開けるようにする
- Google Sheets等の確認画面からreceiptを検索し、証憑を閲覧できるようにする
- private Storageのため、閲覧時には認証付きdownloadまたは期限付きsigned URLを生成する

signed URLそのものは期限切れになるため、DBの正本にはStorage bucket/pathを保存する。

## 検索性

`receipts`に日付・金額・取引先を独立カラムとして保持する。
不明項目はNULLを許容し、要確認一覧から追跡する。

Google Sheetsを索引簿的な確認画面として使う場合も、正本はSupabaseに保持する。

## 保存形式

- 紙スキャン: JPG / PNG / PDF
- 電子取引: 受領した元のPDF等を原則そのまま保存
- OCR/AI抽出JSON: 補助データとして保持できるが、原本証憑の代替とはしない

## 2025年度移行時の扱い

- MF CloudBoxファイル一覧918件をインデックス化済み
- FY2025証憑218件を仕訳218件へリンク済み
- 日付不明34件は推測せずNULLで保持
- Storage実体未保存の原本・取込ファイルは年度末までに補完する
