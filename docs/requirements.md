# 要件・スコープ

## 目的

- akmic合同会社の会計処理をMFクラウドから段階的に自社管理へ移行する。
- 会計専用Supabaseプロジェクトを作成し、そのPostgreSQLを会計データの正本、Storageを証憑本体・取込原本の保存先とする。
- Google Sheetsは確認・照合・集計用とし、正本にはしない。
- 仕訳、証憑、銀行明細、カード明細、取込元ファイル、照合結果まで追跡できるようにする。
- 確定後の仕訳は直接更新せず、反対仕訳または調整仕訳で履歴を残す。
- 自動照合で一意に決められないケースを無理に1対1へ結び付けない。

## 対象

### 2021年度～2024年度

- MFクラウド由来の過年度仕訳をSupabaseへ移行済み。
- 2024年度を基準年度として、総勘定元帳・試算表・月次PL/BSを詳細照合済み。
- 過年度は原則として参照・検証用とする。

### 2025年度（2025-11-01 ～ 2026-10-31）

- MFクラウドを正式な会計処理の基準として継続する。
- MF API仕訳をSupabaseへ取り込み、自前集計・証憑・カード・銀行と照合する。
- 現在のMF仕訳取込範囲は2025-11-01～2026-09-27。
- 年度末に2026-09-28～2026-10-31の追加仕訳を再取得し、最終照合する。
- 決算・申告・最終バックアップ・復元確認後にMFクラウド解約可否を判断する。

### 2026年度（2026-11-01 ～ 2027-10-31）

- Supabaseを正式な会計DB・証憑保存基盤として運用する。
- GMOあおぞらネット銀行および法人カードの明細はCSV取込を基本とする。
- 法人経費はGMOあおぞらネット銀行のデビットカードを基本決済手段とする。
- Google Sheetsで未照合・仕訳候補・月次集計・帳票を確認する。
- 自動仕訳は候補生成までとし、当面は人が確認してpostedにする。

## 機能要件

1. 会計マスタ
   - 会社
   - 会計年度
   - 勘定科目
   - 補助科目

2. 仕訳
   - 仕訳ヘッダ + 複数明細
   - draft / posted / reversed
   - draft作成中は一時的な借貸不一致を許容
   - draft → posted時に借方合計 = 貸方合計をDBで検証
   - 元データ（MF、銀行、カード、手入力）の追跡
   - posted後の直接更新・削除禁止

3. 証憑
   - JPG / PNG / PDF等の原本またはスキャン画像をprivate Storageに保存
   - receipt_code
   - transaction_date
   - amount
   - supplier_name
   - original_filename
   - MIME type
   - Storage bucket/path
   - SHA-256
   - 登録日時
   - 紙スキャンか電子取引原本かの区分
   - 仕訳との多対多紐付け
   - 不明項目は推測せずNULL/要確認として保持可能

4. 外部明細取込
   - MFクラウド
   - GMOあおぞらネット銀行CSV
   - 法人カードCSV
   - 取込原本をStorageに保存
   - ファイルハッシュと取込日時を記録
   - source_record_id / source_row_hashで重複取込を防止

5. 照合
   - カード: direct / group / review / unmatched
   - 銀行: direct / pending_journal / review / unmatched
   - 1対1が確定できない同日同額等はreconciliation groupとして集合照合
   - 銀行実績が先行しMF仕訳未取込の場合はpending_journalとする

6. 帳票
   - 総勘定元帳
   - 試算表
   - 月次PL / BS
   - 年次PL / BS
   - MFとの比較検証

7. Google Sheets
   - 未照合一覧
   - 証憑リンク
   - 仕訳候補
   - 月次集計
   - 試算表・PL・BS確認
   - Sheets側は編集用正本にしない

8. 監査
   - 作成・取込・確定・反対仕訳・紐付け等の履歴
   - 証憑本体の原則上書き禁止
   - 訂正は新規証憑レコードを作成し、旧レコードとの関係を残す
   - 本番DDL/DML変更は原則migrationで管理する

## 非機能要件

- 会計用Supabaseは他用途（特にスロット分析）と別プロジェクトにする。
- Database、Storage、Auth、APIキー、接続情報を他プロジェクトと共有しない。
- 会計データと証憑は原則private。
- `accounting` schemaはData APIへ不用意に公開しない。
- `anon` / `authenticated` からの直接アクセスは初期段階では許可しない。
- 公開クライアントにservice role / secret keyを置かない。
- exposed schemaを使う場合はRLSとauthorization設計を先に行う。
- 証憑Storage bucketはprivateとし、閲覧は認証付きdownloadまたは期限付きURLを利用する。
- バックアップおよび復元確認手順を持つ。

## 電子帳簿保存法への対応方針

本システムは、電子帳簿保存法における真実性・可視性・検索性を意識して設計する。

- 日付・金額・取引先で検索できるメタデータを保持する。
- 電子取引で受領したデータは電子データのまま保存する。
- 紙書類をスキャナ保存として扱う場合は、別途要件を満たす。
- 制度改正があり得るため、本番運用開始前と年度切替時に国税庁の最新要件を確認する。

詳細は [electronic-bookkeeping.md](electronic-bookkeeping.md) を参照する。
